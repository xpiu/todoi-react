# Todoi Design System

Todoi is a kanban-style task manager: boards of lists, cards ("items") you drag between them, and a detail overlay that opens when you click an item. The product targets a **familiar, stable, predictable** feel — conventional kanban idioms, system fonts, a vivid high-chroma palette with full light and dark modes, small fast animations.

**Sources:** three product screenshots provided by the user — `uploads/board.png` (the board view), `uploads/item-overlay.png` (item detail overlay), `uploads/item-overlay-with-checklist-items.png` (item overlay with subitems/checklist). No codebase, Figma, logo, or font files were provided. Layouts and values in this system are measured from those screenshots; branding, naming, and copy are original to Todoi.

**Planned stack (for consumers):** React + Zustand front-end, IndexedDB persistence, custom back-end. Components here are cosmetic recreations, not production code.

## Hierarchy vocabulary (canonical — always use these terms)

`Account -> Group -> Project -> List -> Item -> Subitem`

- **Account:** top-level container and/or billing boundary. May represent an individual, company, organisation
- **Group:** comparable to a Trello Workspace or Linear Team.
- **Project:** comparable to a Trello Board.
- **List:** comparable to a Trello List or Linear Workflow status.
- **Item:** comparable to a Trello Card or Linear Issue.
- **Subitem:** comparable to a Linear Sub-issue.

In UI copy always say "item", "list", "project" — never "card", "column", "board" (those words may describe visuals in internal docs, but user-facing copy uses the canonical terms: "Add an item", "Add another list").

## CONTENT FUNDAMENTALS

- **Casing:** sentence case everywhere — buttons ("Add an item", "Hide checked items"), section headings ("Comments and activity"), list names as the user typed them.
- **Voice:** second person, friendly-instructive, plain. Helper copy speaks to "you" and "your team": "Drop new requests here so nothing gets lost." Never corporate, never jokey-random.
- **Labels are verbs first:** "Add", "Edit", "Delete", "Share", "Hide details". Single words where possible; verb + noun where needed ("Add an item").
- **Placeholders** are invitations: "Write a comment…", "Add a more detailed description…", "Search".
- **Timestamps** are relative and lowercase: "just now", "55 minutes ago"; absolute dates as "Jan 10, 2020".
- **Activity entries** are sentences built around a bold actor name: "**Flo Zuallaert** moved this item from Blocked to Ongoing".
- **Emoji:** allowed in user-authored content (item titles, comments); never in system chrome, buttons, or labels.
- **Counts** shown as plain numerals ("7") and fractions ("2/6"); percentages as "33%".

## VISUAL FOUNDATIONS

- **Color model — one chrome, two grounds:** the whole app frame — top bar, sidebar, sub-navbar, board floor and list/calendar headers — is one cornflower (`--chrome-canvas` #7c9fff, oklch(.72 .15 268)) with **near-black navy ink** (`--chrome-text` #0b1233, 7.2:1; `--chrome-text-dim` rgba(11,18,51,.82), 5:1). Content sits on it in warm cream (lists #f8f5ee, panels #fbf8f2) and white cards with navy ink (#131f45 / #3b4a70). `--chrome-topbar` (#12215e) is the navy accent used by `Toast` only; the top bar itself is canvas-colored. Never put white text on the light chrome.
- **Themes × modes (two axes, both on `<html>`):** `data-theme="standard|minimal"` is the app theme (look and feel), `data-mode="dark|light"` the color mode inside it. Standard · dark is the default: its values ship on `:root`, so a page with no attributes renders Standard dark. Every color and shadow token is defined four times, once per theme × mode, in `tokens/themes/<theme>.css` (`standard.css`, `minimal.css`); `tokens/colors.css` holds only the theme-independent aliases and fixed ink. Scopes: `:root`/`[data-theme="standard"]` → Standard dark · `[data-theme="standard"][data-mode="light"]` (and `html:not([data-theme])[data-mode="light"]` for mode-only pages) → Standard light · `[data-theme="minimal"]` → Minimal dark · `[data-theme="minimal"][data-mode="light"]` → Minimal light. Components consume token names only — never a theme file, never a hex, never a mode selector for styling; a theme that needs more than new values scopes component rules on `[data-theme="minimal"] .td-…` (its `shape & density` block is the place for radius/spacing/elevation overrides). The JS twin is `components/core/Themes.jsx` (`THEMES`, `THEME_REGISTRY`): one entry per theme naming its Background and Foreground palettes per mode (`STANDARD_*` / `MINIMAL_*` constants). **Minimal is "Ledger"** (from `explorations/minimal-theme-board.html`, option B): one paper color per mode (white `#fff` in light, near-black `#141415` in dark) with **no Foreground option**, black-versus-grey type (ink `#000`/`#f2f2f3`, metadata `#707070`/`#8b8b90`), a 12–14% hairline as the only separator, no fills and no shadows, red only for overdue dates; the "action blue" tokens resolve to the ink so primary buttons, checkboxes, focus rings and selection stay monochrome. Type switches to Inter (UI) and Geist Mono (keys, counts, day numbers) at 13px/1.45 with 500 as the heaviest weight (`tokens/typography.css`, fonts in `assets/fonts/`). Everything that is not a token value — the one 48px chrome row with icon-only tools and views, the 196px hairline sidebar without icons, lists as ruled columns in a 24px gutter with cards as rows (title, then one grey line of words: labels, date, initials, count, priority, mono key; done grey with no check; covers as a bare 96px strip), the ruled List and Calendar views — lives in `tokens/themes/minimal-components.css`, scoped `html[data-theme="minimal"] .td-…`. Class hooks components expose for it (no visual effect in Standard): `.td-card-body/-title/-labels`, `.td-prio-text` (the priority word, hidden by default), `.td-due[data-state]`, `.td-label`, `.td-avatar[data-initials]`. Colorize Board columns adds no fills in Minimal. Adding a theme = one CSS file + one `@import` in `styles.css` + one registry entry. The **Themes × modes** card shows all four scopes; the **Theme parity audit** card (Colors group) live-checks every token for a missing light value, orphans, token-set drift between themes and hardcoded hexes in component code — keep it green.
- **Dark mode (Standard):** pages ship `data-theme="standard" data-mode="dark"` on `<html>` and the shared appearance store falls back to dark when nothing is stored (localStorage `td-mode` wins if the user has toggled). Full token parity per theme, `color-scheme` set per scope. Chrome goes neutral black (topbar #0b0b0c, canvas #161617) with white chrome text (`--chrome-text` flips to #fff), content flips to elevated neutral-black surfaces (lists #1a1a1b, cards #242425, overlay panel #1f1f20), the ink ladder inverts (#f2f2f3 → #6e6e76), action blue lightens (#3d84ff; hover gets lighter, not darker), labels and semantic colors brighten one step, neutral alphas flip to white-based. Components must use tokens only — never hardcoded hexes; the fixed-ink tokens (`--chrome-selected-text`, `--label-text`, `--btn-inverse-*`) stay dark in every scope and carry a `/*fixed*/` marker in `tokens/colors.css`. "Dark is the default" in a component stylesheet is written `html:not([data-mode="light"]) …`, never `[data-mode="dark"]` (the attribute is absent until the store mounts).
- **Primary action blue** #264de3 (checkboxes, links, focus rings, primary buttons). Hover #1a3bc9, active #10289e.
- **Distance from Trello (deliberate):** Trello's blues sit at L .54–.56 with white text (classic #0079BF hue 245°, Atlassian #0C66E4 hue 259°). Todoi's chrome is a full lightness step lighter (L .72) with navy ink on it instead of white, the lists are warm cream instead of cool grey, and the action blue is deeper (L .50). Do not darken `--chrome-canvas` toward L .55 with white text — that is Trello's board. Analysis and rejected directions: `explorations/chrome-blue-options.html`, `explorations/light-mode-joyful.html`.
- **Appearance preferences (per device, never shared config):** one store, `useAppearance()` in `components/core/Appearance.jsx` (`APPEARANCE.use()` from the bundle), holds theme (Standard · Minimal), mode (Dark · Light), the Background (chrome canvas) and Foreground (list · card · panel: Carbon · Graphite · Pitch in dark; none in Standard light) picks **per theme × mode slot**, Show item IDs, Show labels, Show Status on items, Sidebar on left side (`td-sidebar-left`; the `Sidebar` docks on the left edge and the `TopNavbar` toggle leads the bar as panel-left — both read the store, so no host wiring is needed; `<html data-sidebar-side>` mirrors it), and **per theme** Colorize Board columns and Suggest shortcuts (Standard: both on; Minimal: both off — the first switch to Minimal lands with them off, and a pick made there is remembered under `td-colorize-columns-<theme>` / `td-suggest-shortcuts-<theme>`); persists the rest under `td-theme`, `td-mode`, `td-bg-<theme>-<mode>`, `td-fg-<theme>-<mode>` and the other `td-*` keys (the old `td-canvas` / `td-canvas-dark` / `td-fg-dark` and a light|dark `td-theme` migrate on first read) and applies the DOM effects (`data-theme`, `data-mode`, `--chrome-canvas`, surface overrides, `data-colorize-columns`). `ap.set("background", hex)` always writes the slot you are looking at; switching theme or mode brings that slot's picks back. Two surfaces read and write it: the **SubNavbar Style dropdown** (Theme and Mode `Segmented`s, Background/Foreground `SwatchGroup`s, five checkboxes, and a "More options" footer when `onOpenAppearance` is wired) and **Settings › Appearance** (Style: Theme · Mode · Background · Foreground / Layout: Sidebar on left side / Items: Show item IDs · Show labels · Show Status on items · Colorize Board columns / Shortcuts: Suggest shortcuts / Defaults: Reset appearance). Never keep a second copy in app state.
- **Background swatches (Style menu):** per theme × mode from `Themes.jsx`. Standard light is five light colors that all take navy ink at ≥5:1 — Butter #f6d653 (first, the default), Cornflower #7c9fff (the CSS token fallback for pages without the store), Lavender #b191ea, Mint #5ed8a9, Peach #fca676; Standard dark is Graphite (default) · Midnight blue · Deep indigo · Dark teal · Dark plum. A host-supplied `canvasColors` / `darkCanvasColors` list must keep the ink property; the chrome text does not switch per swatch.
- **Ink ladder:** #131f45 body → #3b4a70 secondary → #5a6a8c icons/meta → #8091ad faint borders.
- **Label palette:** 8 solids (green #1ed07c, yellow #ffd024, orange #ff8f3e, red #ff5a4f, pink #ff5ca8, blue #3d7efc, teal #14c3ea, lime #96da14). Compact form: 40×8px bars, radius 4. Expanded form: 32px chips with dark ink text.
- **Semantic greens:** #1fbd53 done check icon; #42a12e due-date pill (white text).
- **Type:** system UI stack only (`--font-ui`); no webfonts shipped. Scale 12/14/16/18/20/24. Body 14/20. Section headings 16 semibold. Item overlay title 24 semibold. Board title 18 bold white. Weights: 400 body, 500 buttons, 600 headings, 700 board title.
- **Spacing:** 4px base grid; 8px card padding unit; 12px gaps between lists; lists fixed 272px wide.
- **Radii:** 4px label bars/pills, 8px cards/buttons/inputs, 12px lists and overlay panel.
- **Stacking:** one tokenized ladder in `tokens/elevation.css` — `--z-raised` 1 → `--z-hover-control` 20 → `--z-above-content` 30 (sidebar) → `--z-menu` 60 / `--z-menu-nav` 70 / `--z-menu-detached` 80 → `--z-modal` 100 → `--z-sheet` 150 (phone bottom sheets) → `--z-menu-toolbar` 190 (app-bar dropdowns) → `--z-palette` 200 → `--z-drag` 250 (touch drag ghost) → `--z-toast` 300. Components never write a raw z-index: `z-index:var(--z-menu,60)`, fallback equal to the token. Rungs are spaced so consumers can slot layers between them; a menu trapped in a scroll/transform ancestor uses `position:fixed` + `--z-menu-detached`. Full map: the Stacking ladder card.
- **Shadows:** cards `0 1px 1px rgba(7,26,69,.25), 0 0 1px rgba(7,26,69,.31)`; dragged/raised `0 8px 12px rgba(7,26,69,.15)`; overlay `0 8px 40px rgba(7,26,69,.35)`. No inner shadows.
- **Backgrounds:** flat solid colors. No gradients, patterns, textures, or background imagery in chrome. Item covers may carry user imagery (full-bleed at top of card/overlay, `--surface-cover` #555b6b letterboxing behind them).
- **Borders:** hairline `rgba(7,26,69,.14)` on inputs/outline buttons; divider `rgba(7,26,69,.08)`. Cards have shadow, not border.
- **Hover states:** background shifts, never movement — neutral fills go .06→.14 alpha; chrome fills are navy alphas .10→.16→.24 (`--chrome-hover/-active/-pressed`; white alphas in dark mode); cards show a 2px #264de3 outline. Press: one step darker, no shrink.
- **Animation:** small and predictable. 100–150ms `cubic-bezier(.2,0,0,1)` for color/background; overlay fades + settles (opacity 0→1, scale .98→1, 200ms); tooltips wait `--duration-slow` (400ms). No bounces, no spring physics. **Reduced motion** is one global rule in `tokens/motion.css` (`prefers-reduced-motion: reduce` collapses every animation and transition to a frame; delays stay) — components never add their own `@media` for it.
- **Minimal theme coverage:** every surface the kit reaches is themed in `tokens/themes/minimal-components.css`, grouped by area (top bar, sidebar, board, list, calendar, chrome rows, shared controls, tooltips, account pages, Inbox, floating layers incl. the Create menu, toolbar menus Filter/Sort/Members, auth pages, command palette, search dropdown, item overlay). Rules of the Ledger look: square corners, hairline rings instead of shadows, grey words that go ink on hover, initials in mono instead of avatar discs, colour only as a 6px label swatch or overdue red. Any new component needs its Minimal block here before it ships; audit it in both modes through the Style menu (the Appearance store owns `data-theme`/`data-mode` — flipping the attributes by hand leaves the remembered Background behind).
- **Tooltips:** one styled hint for icon-only controls — `IconButton`/`MenuButton` `tooltip` or `<Tooltip>` around anything else (`components/core/Tooltip`): navy pill (`--ink-900`, text `--surface-card`, flips with the theme), 14/18 medium, 400ms delay, caret; sides `bottom` (default) · `bottom-end` (right edges, the sidebar ⋯) · `top` (bottom bars) · `left` (rails). 2–4 words, sentence case; never the only label, never on text (truncated read-only values keep the browser's `title`), never on disabled controls. **Never the browser's `title` balloon on a control** — every icon-only control in the system carries `data-tip` (`tipProps(text, side, labeled)` from Tooltip builds the props); a control whose text label a theme hides (Minimal's icon-only toolbar) adds `td-tip-labeled`, which keeps the hint off while the label shows and on once the theme hides it. Sidebar nav rows carry a 2–4 word `tip` under the row; their longer `tooltip` feeds only the aria-label. Anything longer is a `footerLead`, an EmptyState hint or a SyncNotice. Card: Tooltips & hints (Interaction).
- **Transparency & blur:** alpha fills only (chrome buttons, backdrop `rgba(7,26,69,.6)`); no backdrop blur.
- **Overlay layout:** 880px panel, radius 12; left content column + 376px right rail ("Comments and activity") split by a hairline divider; optional 128px cover strip up top.
- **Imagery:** user-supplied, unstyled (no duotone/grain). Letterboxed on the cover strip.
- **Sample covers:** `assets/covers/*.svg` only — every sample cover is an SVG placeholder on a 512×162 viewBox (browser chrome + monospace `photo` slots). No raster covers in the repo; real imagery is the consumer's to drop in.

## ICONOGRAPHY

- Style: 2px-stroke outline glyphs, round caps, 16px in badges/meta (color #5a6a8c), 20px in section headers, 24 grid.
- **Substitution flag:** the source screenshots use a proprietary icon font we cannot copy. We use **Lucide** (ISC license) from CDN as the nearest match (same stroke weight and style): `https://unpkg.com/lucide@0.454.0/dist/umd/lucide.min.js`. In plain HTML use `<i data-lucide="clock"></i>` + `lucide.createIcons()`; in React use the `Icon` component (`<Icon name="clock" />`), which renders from the loaded Lucide registry.
- Common glyphs: clock (dates), square-check-big (checklists), align-left (description), paperclip (attachments), user-plus (members/share), tag (labels), message-square (comments), circle-check (done), plus, x, ellipsis, chevron-down, search, bell, circle-help, lock, star, zap, list-filter, image; kanban (board view), calendar (calendar view), filter (funnel), arrow-up-narrow-wide (sort), palette (style); sidebar: panel-right/panel-left (collapse toggle), users (Groups), kanban (Projects), inbox (Inbox), per-project glyphs in label colors (e.g. megaphone, rocket) — never colored square swatches.
- No icon font of our own, no emoji-as-icons, no hand-drawn SVGs. Unicode characters are not used as icons.
- **No logo exists.** Render the brand name "Todoi" in plain type (600 weight, white on chrome) wherever a mark would go. Do not invent a logomark.

## INTERACTION & KEYBOARD

- **Item keys:** every item carries a short key ("TD-112") in mono (`--font-mono`, 11–12px, `--ink-400`) — pinned to the right edge of the card's last row (badge row, or labels row when that's the only one), beside the list picker in the overlay, and in palette rows. Hovering a card key shows a small copy popover; clicking copies the key without opening the card. Keys are for referencing items in commits and chat; titles stay the primary label.
- **Keyboard model (board & list):** cards and rows are focusable; each view is ONE Tab stop (`KeyNav` roving tabindex — the last-focused item keeps focus rights, interior controls of other items are skipped), so Tab reads: top bar → search → view switcher/toolbar → content → sidebar. Arrows move focus between items and lists (J/K within a list), Enter or Space opens, Esc closes the overlay. The `:focus-visible` ring reuses the 2px blue hover outline.
- **Quick-add (N):** N opens the quick-add field in the list you are in (the focused item's list, else the first visible one) instead of creating a blank "New item". The field parses inline tokens while you type and previews them under the input as the same quiet meta row a card shows (label bar, avatar, flag, clock + date, list glyph — no pills, no × controls, no legend; the grammar is taught by the ? dialog): `#label` (unknown names create a new label, marked "new label"), `@assignee` (nickname / first name / prefix), `!priority` (`!urgent !high !medium !low` or `!1`–`!4`), `due <date>` / `by <date>` (today, tomorrow, weekday, `12 sep`, `sep 12`, `in 3 days`, `next week`, ISO), and `>List` to pick the destination. Edit the text to change a property; Enter adds and keeps the field open; Esc closes. Parser: `parseQuickAdd` in `components/core/QuickAdd.jsx`; the grammar is documented in `ShortcutsDialog` ("Quick-add syntax") from the same registry.
- **Multi-select & bulk actions:** S toggles the focused item, shift+↑↓ (or shift+J/K) extends, ctrl/cmd+A selects the whole list, ctrl/cmd+click toggles, shift+click ranges within a list, Esc clears. Selected cards/rows get the 2px blue ring on `--blue-100`. While 1+ items are selected `BulkBar` sits bottom-center (Toast keeps bottom-left, ShortcutHint bottom-right) with Move to · Priority · Label · Assign · Done · Delete — each applies to every selected item with ONE undo toast. Move to ends with a divider and two panel rows, "Move to another project…" / "Copy to another project…", which swap the option list for a `ProjectPicker` (see MOVING BETWEEN PROJECTS). With a multi-selection that includes the focused item, D / ⌫ / 0–4 apply to the whole selection too. Selection keys come from `KeyNav` (`onItemSelect`).
- **Saved views:** hidden by default — a 4th icon-less "Views" segment (after a thin divider) in the List / Board / Cal. group toggles the row (`SubNavbar` `savedViewsToggle` / `savedViewsOpen` / `onSavedViewsToggle`; remembered in localStorage `td-saved-views-open`, auto-opened when a shared saved-view link loads). When open, `SavedViewTabs` sit on their own chrome row directly under the toolbar (the kit's `TDViewsBar` with `open`; `SubNavbar` can also inline them via `savedViews` when the toolbar has room) — "All items" plus one tab per saved view. A view captures view type + filters + sort per project; shared views carry a `users` glyph, personal ones don't. `Save view` (bookmark-plus) appears when any filter or sort is active; the tab's ⋯ / right-click menu offers Copy link, Update with current filters (blue dot when the live state drifts), Rename, Share / Make it only mine, Delete (undo toast). The URL mirrors the state (`?p=p1&view=sv1` for a clean saved view, `?p=p1&v=board&f=label:design&s=items.due.asc` for ad-hoc state) via `history.replaceState`, so filters survive a reload and a copied link reproduces them. Group-by is not part of the kit yet; when it lands it joins the definition.
- **Platform-aware key labels:** `SHORTCUTS.keyLabel(tok)` renders `ctrl` as ⌘ on macOS/iOS (matching accepts either); `SHORTCUTS.modLabel` feeds the toast's undo hint. ShortcutsDialog and the keyboard guideline card use it.
- **Shortcut map (Trello/Linear conventions):** N opens quick-add where you are; ⇧N adds a list; E opens the focused item with the title in edit (rename); D toggles done; 1–4 set priority Urgent/High/Medium/Low, 0 clears; ⌫ deletes with undo; / focuses search; F opens the filter menu; X clears filters; Z (or Ctrl+Z) undoes the last change (up to 10 back, this session); ? opens `ShortcutsDialog`, the built-in cheat sheet; G-then-B/L/C/I/P/G jump to Board/List/Calendar/Inbox/Projects/Groups. Single-key shortcuts pause while typing and while a dialog is open. **The whole map lives in `components/core/Shortcuts.jsx` (`SHORTCUTS`: display sections + event matchers)** — `ShortcutsDialog`, the keyboard guideline card, `KeyNav`, `ItemOverlay`, and the ui-kit shell all render and match from it. Change a shortcut there and every surface follows; never hardcode a key check in a component.
- **Moving items:** Ctrl/Cmd+arrow moves the focused item (up/down within a list, left/right across lists at the same position; focus follows). Cross-list moves raise a toast with Undo (Ctrl+Z works while it shows); within-list moves announce through a visually-hidden `aria-live` region.
- **Drag & drop:** items drag within and across lists in Board and List view; subitems drag to reorder within their item (List view rows and the overlay checklist) and drop onto another item's row to move there. Cues are deliberately quiet: the source dims to ~45%, a 2px action-blue line marks the insertion slot (floating in the 8px gap on the board, an inset edge line on rows), and an item row targeted for subitem re-parenting fills `--action-subtle` inside a 2px blue inset ring. No tilt, no drop shadows beyond the browser drag image. Cross-list drops and re-parenting raise the undo toast; same-list drops announce via the `aria-live` region.
- **Files onto items (Board and List):** `useFileDropTargets(onFiles, {selector})` (`components/overlay/Attachments.jsx`) sits on the same view root as the item-drag handlers — file drags carry `Files`, item drags don't, so they never collide. The card or row under the pointer gets `.td-file-target`: a dashed 2px action-blue ring inset, `--action-subtle` fill and a small "Drop to attach" chip (dashed = attach, like the overlay's drop sheet; solid = move). Over a list body, header, subitem row or the canvas the drop is refused (not-allowed cursor) — a file never lands on a list. The drop calls `onFiles(files, itemId)`; the consumer runs the same upload queue as the overlay (`attachFiles`; progress and failures show there when the item is opened), bumps the card's paperclip count and raises one toast. Pointer only. Card: Drop files on items (Interaction).
- **Command palette:** Ctrl/Cmd+K opens `CommandPalette` — search by key, title, or list; ↑↓ + ↵ to open. Before a query it lists the current project's items; a query searches every item the viewer can open — their member projects (subitems included, "Subitem of …" as context) and their own Inbox — through the bounded `GET /api/search`. A result opens by id (`app/search.ts` `useOpenResult`, shared with the top-bar search): a project item opens its overlay (in the current project the view, filters included, stays underneath), an Inbox item opens the Inbox at that item. "Searching…", offline and failure each say so instead of a false "No items". The app owns the shortcut and skips it when focus is in an input. Shortcut hints render as mono kbd chips (`.td-kbd`); the full map lives in `ShortcutsDialog` (?).
- **Shortcut suggestions (on by default in Standard, off in Minimal):** the third Style-menu checkbox, "Suggest shortcuts" (localStorage `td-suggest-shortcuts-<theme>`), turns on `ShortcutHint` — one 28px card-white pill fixed bottom-right (the Toast owns bottom-left) with mono kbd chips. It appears only after a *pointer* action a key could have done (clicking a view segment → `G then B`, Add an item → `N`, Filter → `F`, dragging an item across lists → `ctrl + ← →`, opening an item → `ctrl + ↵ · esc`) or when the pointer rests ~900ms on an item (`↵ open · E rename · D done · ⌫ delete`). Never while typing, dismissed and suppressed by any keypress, one at a time, gone after 6s, each situation at most 3 times ever (`td-hint-seen`; re-enabling resets). `aria-hidden` — a pointer-user nudge, not an announcement. Registry + hook: `components/core/ShortcutHint.jsx` (`SHORTCUT_HINTS`, `useShortcutHints`); situations: the Shortcut suggestions card.
- **Toasts:** `Toast` sits fixed bottom-left on navy (`--chrome-topbar`), `role="status"`, auto-dismisses after ~5s (hover pauses). One at a time. A toast confirms an outcome **only after the server has it** (Archived, Deleted, Created, Copied…), with Undo where undoable. Its one other job is the **fallback explanation of a failed request** that has no form of its own to show it in (`circle-alert`, the server's reason, "Sign in" when the session ended): the query client raises it for every failed mutation unless the call passes `quiet` because it shows the reason itself. Where there is a draft or a form (create project/group, invite, save view, comment, title, description, accept invite), the failure is an `InlineError` beside it and nothing typed is cleared.
- **Undo history (minimal by design):** a session stack behind Ctrl+Z (`useFeedback`, `src/client/app/feedback.ts`, depth 10, LIFO, no redo, nothing persisted). Every outcome that raises an undo toast also pushes `{message, restore}`; Z / Ctrl+Z restores the top **whether or not the toast is still showing**, removing it only after success. Failed restores remain retryable; repeated Undo waits for the pending restore. Deletion Undo restores the existing record and relationships instead of recreating it. Each undo raises a confirmation toast — "Undid: moved “…” to Ongoing", `undo-2` glyph, quiet `meta` "n more", and "Undo more · ctrl Z" while entries remain. The toast is the whole GUI: no history panel, no redo button. Other entries may restore snapshots, so undoing an older step can also revert later edits to the same records — the confirmation names it. Typing, comments and settings never enter the stack; the stack clears when the project or screen changes. Card: Undo history (Interaction).
- **Overdue:** an overdue, not-done item shows the red due pill — no additional card treatment.
- **Filtering:** active filters always render as `FilterChip`s in a row under the SubNavbar with "Clear filters" — the board never silently looks empty. Label filters OR together, then AND with Overdue; list counts read "2 of 7" while filtered.
- **Inline editing primitives (one surface for every dropdown):** `Popover` (components/core) is the anchored floating card every menu, picker and panel sits on — card-white, radius 7, `--shadow-overlay`, 4px padding, 150ms fade + 4px settle; it owns outside-pointer close, a *captured* Escape (so the item overlay stays open when a menu inside it closes), viewport flip, focus return to the trigger, and the z-tier (`menu` → `--z-menu`, `nav` → `--z-menu-nav`, `detached` → `--z-menu-detached` + `position:fixed` for anchors inside scroll/transform ancestors, `toolbar` → `--z-menu-toolbar`). On top of it: `Menu`/`MenuItem`/`MenuDivider`/`MenuNote` (30px rows, 13/18, 15px `--ink-600` glyph, `--action-subtle` hover, trailing check on the picked radio row, `danger` rows, `drill` rows that swap in a sub-view, ↑↓/Home/End/first-letter roving, single keys never leak to the shortcut map), `MenuButton` (trigger + Popover + Menu — the ⋯ menu), `Select` (one-of-N picker: outline Button trigger showing the picked option's glyph + label + chevron, menuitemradio rows, automatic filter field above 8 options, `footer` rows like "Create new list"; `variant="chrome"` on the app bar) and `DatePicker` (due-date editor: clock Button trigger → typed-date field that speaks the quick-add `due` grammar via `resolveDate`, Today / Tomorrow / Next week, the `DateCalendar` month grid — 7×32px days, Monday start, today ringed, picked day filled action blue, arrow keys move the day — and Clear; ISO in/out, `formatDate` → "Sep 12, 2026", `state="overdue"|"complete"` tints the trigger like `DueDatePill`). **Never hand-roll another `position:absolute` card, outside-click or Escape effect, and never a native `<select>` or `<input type="date">`.** Adopted so far: the item overlay's Status, list picker, Priority (Selects), Dates (`DatesPicker`, `onSetDates`; `onSetDue` still accepted), Repeat, Labels, Assignees, Cover, Relations (their own pickers — see ITEM EDITING) and ⋯ (MenuButton), the calendar period picker, `ItemCard`'s ⋯ (`onMenuAction`), the list-head ⋯ (`ListActionsMenu` now returns MenuItems for a `MenuButton` in `ListColumn`, Icon and Status role as drill sub-views), `SavedViews` (⋯ menu + Save-view Popover), and in the UI kit `TDRowMenu` (now a MenuButton with a drill icon grid) and `TDSelect` (replaces every settings `<select>`). Still on their own code and next to migrate: sidebar/top-bar menus, and the Share/Style/Search/Filter/Sort/Members panels (Popover shell only, content stays custom). Full map: the **Inline editing — adoption map** card (Interaction group).

## ITEM EDITING (overlay properties and content)

Everything an item carries is edited in the overlay, in place, on the shared Popover — no property dialogs. Minimal and functional: a trigger reads its value in words, the panel is one screen, destructive steps confirm inline on the row. Specimens: the **Item property pickers** and **Item content editing** cards (Components group); the assembled result is the **Item overlay** card.

- **Aside order:** list · Status · Priority │ Dates · Repeat · Labels · Assignees │ Attachment · Cover · Relations │ Watch. Hairline dividers (`.td-aside-div`) separate the groups. A missing callback hides its row.
- **Assignees — `MemberPicker` + `AvatarStack`** (core): multi-select over a search field; assigned people sort first; trigger shows a 20px `AvatarStack` + first names / nicknames. Value = member keys (id, else name). "Clear assignees" under a divider. Cards keep showing the same stack via `ItemCard.assignees`.
- **Labels — `LabelPicker`** (core): search + check rows (24×8 color bar); a pencil on hover edits name/color/delete in a one-screen form (8 swatches, live chip preview, two-step Delete); an unmatched query offers "Create “…”" and picks the new label at once. `nextLabelColor` hands out the first unused palette color. Settings › Labels stays the overview; the picker is the everyday path.
- **Description — `DescriptionEditor` + `Markdown`** (overlay / core): view state renders the Markdown subset the GitHub sync writes (# ## ### · - / 1. · - [ ] tasks · > · ``` · **bold** *italic* ~~strike~~ `code` links, @mentions, item keys); click to edit → auto-growing textarea, quiet toolbar (bold · italic · strike · code · link │ bullets · numbers · tasks · quote · heading, mono toggle), ctrl+B/I/K, Enter continues lists, ctrl+↵ saves, Esc cancels, "Unsaved" hint. Nothing writes until Save; the overlay's ctrl+↵ save-and-close commits a pending draft. No raw HTML, images or tables.
- **Dates — `DatesPicker`** (core, replaces `DatePicker` in the overlay): one field for start + due + due time. Trigger: "Sep 10 – Sep 12, 2026 · 14:00". Panel: Due field, "Add start date" → Start field, Time field once a due exists ("14:30", "2pm", "noon" → 24h), quick picks, one `DateCalendar` writing into the active field (start auto-advances to due; the span shades `--blue-100` between the two — `DateCalendar.range`), Clear. Start after due drags due along; clearing due drops the time. `formatDateRange`, `parseTime`, `formatTime`. The calendar view already draws start→due spans.
- **Repeat — `RepeatPicker`** (core): the rule as a sentence ("Every 2 weeks on Mon, Wed until Dec 31"). Presets worded from the due date (Daily · Weekly on Fri · Every weekday · Monthly on the 12th · Yearly on Sep 12), Custom… (interval + unit segment, weekday discs, Ends never / until / after N), "Doesn't repeat". Value is a plain rule object; **checking a recurring item done is the consumer's move**, with one helper and one cue: `completeRecurring(rule, due, {title, count, today})` returns the next due (reopen the item with it, store `count`) or `ended` (leave it done) plus the toast copy — "Completed “…” — next due Sep 3" (`repeat` glyph, meta "3 of 10" for ends-after rules; "— that was the last repeat" when the rule ends) raised with Undo like any move. Cards and rows show the rule as a 14px `repeat` glyph after the due pill (`ItemCard`/`ListRow` `repeat` = the `describeRepeat` sentence), and `Checkbox recurring` (set by `ListRow` when `repeat` is passed) holds the check for 650ms before the row settles back on the new due — the click is confirmed before the item reopens. The picker never mutates dates. Card: Recurring item completion (Interaction). Shown only when `onSetRepeat` is wired or a rule exists.
- **Attachments — `AttachmentList` / `AttachmentRow` / `Lightbox` / `DropOverlay` + `useFileDrop`** (overlay): rows of 64×48 thumbnail (image preview, or file glyph + mono extension), name, meta ("Added Sep 12 · 240 KB · Cover"); hover reveals Open and ⋯ (Download · Make/Remove cover · Rename inline · Delete with an inline "Delete this file? Delete · Cancel"). Uploading files show a 4px blue `ProgressBar` in place of the meta line, with × Cancel. Each file is its own request (`app/uploads.ts`), so one failure never hides or undoes another: a failed file keeps its row with the reason in danger text, Retry when sending again can succeed (network or server error — not "larger than 25 MB", a quota or an access refusal) and × Remove; the batch raises one toast ("Attached 3 files", or the failure with Retry). Limits live in `shared/uploads.ts`: 25 MB per file (refused before sending), 10 files and one bounded body per request (refused before the API reads it), and a stored-bytes quota per uploader (guests 100 MB). A request attaches all its files or none. Images open the Lightbox (←/→, Esc closes only the preview). Files arrive four ways: the aside Attachment button, the section's Add, a drop anywhere over the panel (white sheet + dashed action-blue frame "Drop files to attach"; in-app drags are ignored), or the Cover picker's Upload. Card badge: `badges.attachments` count.
- **Cover — `CoverPicker`** (overlay): Color (8 label colors + cover grey + navy as 32px tiles) · Image (the item's image attachments as tiles + Upload) · Remove cover. Emits `{color}` or `{src, attachmentId}`; the attachment row's "Make cover" is the same action.
- **Comments — `Comment` + `CommentComposer` / `MentionField`** (overlay): the composer auto-grows, ↵ sends, ⇧↵ breaks a line, typing `@` lists matching members (nickname · first name · full name; ↑↓ ↵/Tab insert "@handle "). Rendered comments are Markdown with mentions highlighted; reactions are 24px pill chips (own reaction on `--blue-100`) plus a smile-plus picker of eight quick emojis (👍 ❤️ 🎉 👀 ✅ 🚀 😄 🙏 — emoji is user content here, never chrome). Action line: Reply (prefills "@handle " + "Replying to" line), and for the author (`mine`, defaults to `author === currentUser`) Edit (inline field, ctrl+↵) and a two-step inline Delete. "· edited" marks edits.
- **Watch:** an aside toggle (eye / eye-off, `aria-pressed`, blue when on) — "Watch" / "Watching". Notification wiring is the consumer's.
- **Relations — `RelationsSection` / `RelationPicker` / `RelationButton` + `ItemPicker`** (overlay / core): three types, stored on both items (`RELATION_TYPES` names each inverse): **Blocked by** (`ban`, red while any blocker is open — `isBlocked`), **Blocks** (`arrow-right-to-line`), **Related to** (`link-2`). The section groups rows by type (status glyph · mono key · title · list; × on hover; "Blocked" flag in the header) and its + opens the picker: type segment + `ItemPicker` (search by key, title or list). Calendar/card treatments for blocked items are not designed yet.
- **Subitems ↔ items:** every checklist row grows a hover ⋯ — Open (the subitem's own key) · Convert to item · Move to another item… (drill into `ItemPicker`) · Delete. The overlay's corner ⋯ gains "Make subitem of…" (drill into `ItemPicker`; the item's key stays). Parent/child is not a relation type.
- **Kit:** everything above is live in `ui_kits/todoi/index.html` (uploads are simulated with a progress timer, relations/watching are in-memory, labels created in the picker join the project's label list).

## MOVING BETWEEN PROJECTS

Items move between lists with the aside Select, drags and Ctrl+arrows, and file from the Inbox by drag; crossing a project boundary is one more picker, not a dialog. **`ProjectPicker`** (`components/core/ProjectPicker.jsx`) is the panel: pick the project (search; glyph in its color, name, group at the trailing edge; a project without lists is inert, "No lists"), then the destination list, with one `MenuNote` saying what travels. It is mounted in two places:

- **Item overlay ⋯** → **Move to project…** (replaces the plain Move row once `onMoveToProject` is wired) and **Copy to project…** (`onCopyToProject`), both drill views beside Duplicate (the in-project copy). Props: `projects` (id, name, icon, color, group, lists), `currentProject` (excluded from the list).
- **BulkBar › Move to** → after the project's own lists, a divider, then "Move to another project…" / "Copy to another project…" as `panel` options (the option list swaps for the picker; its back arrow returns to the lists).

Rules: a **move** takes subitems, attachments, comments and relations along and lands at the end of the picked list; the key stays inside its group and is re-issued from the destination group's prefix when the group differs. A **copy** always gets its own key and starts without comments or activity. Linked-status rules apply as for any move ("— Status set to Doing"). The overlay closes when its item leaves the project; the outcome is one undo toast: "Moved “…” to Social Media › Planned — MP-211" / "Copied 3 items to Dealers & stock › Incoming"; both projects' activity logs get a row. Never from a card's hover menu or a list ⋯ — select, then act. Cards: Move or copy to another project; Bulk action bar.

## STATES (empty, loading, error)

Every view assumes populated data by default; these are the treatments when it is not. All three components live in `components/core/` and use tokens only; the situation table is the **Empty, loading and error states** card (Interaction group).

- **`EmptyState`** — the one block for "nothing to show": optional 22px Lucide glyph in a dim color, one title (14 semibold), at most one hint (13), at most one primary + one quiet action (with an optional mono kbd chip). No illustrations, no emoji. `surface="chrome"` fills the content slot on the canvas: a **project with no lists** ("No lists in this project yet" → Add a list ⇧N, or the one-click starter set To-do · Doing · Done) and a **filtered view with no matches** ("No items match these filters" → Reset filters X; the FilterChip row stays above it and the hint counts what is hidden). `surface="card" compact` sits inside a section: the **first-run Inbox** ("Your inbox is empty" + how capture → drag-to-file works, above the section's own add row). `tone="danger"` is reserved for a **failed load with nothing cached** (red glyph, Retry + Details). A list that merely has no items gets nothing — its "Add an item" row is the affordance.
- **`ViewSkeleton` / `Skeleton`** — loading. Flat `--surface-track` blocks with an opacity pulse only (no shimmer gradient; still under `prefers-reduced-motion`), laid out as the view about to appear (`view="board"` columns + cards, `"list"` sections + rows, `"inbox"` one block) in the space it will occupy. Nothing paints for the first 150ms (`delay`), then the skeleton until data arrives — no minimum display time, no spinner on the canvas. Chrome never skeletons.
- **`SyncNotice`** — a persistent inline notice for a *condition* (a Toast is for an outcome or one failed request, not a lasting state): card-white row pinned to the bottom of the viewport (`placement="inline"` keeps it in flow), neutral hairline border with the tone carried by the glyph only (`danger` red / `warn` yellow / `info` blue), tone glyph, bold message + quiet detail, actions right (quiet secondary → Details, subtle primary → Retry / Reconnect / Resolve, × dismiss). Placed once under the toolbar rows and above the content, same 12px gutter; one at a time, most severe wins; dismissal lasts until the condition changes. Retry shows "Retrying…" on the same button. Copy names the condition then what is safe: "Sync failed — GitHub didn't respond · Your changes are saved on this device and sync when the connection returns. Last synced 12 minutes ago."
- **`ConnectionStatus`** — offline and queued edits, in the app frame. A 28px chrome pill in the `TopNavbar` `status` slot (right of the project nav) that renders **nothing while online with nothing queued**; "Offline · 3" (`cloud-off`) while the connection is down, "Syncing 3…" (turning `refresh-cw`) while the queue drains, "3 edits queued" (`cloud-upload`) when online but paused, and "Synced" (`cloud-check`) for two seconds once the queue is empty. Navy ink on the chrome — tone lives only in the glyph of the menu it opens (warn yellow offline, action blue syncing). The menu (shared `Menu`, nav tier): the condition in bold, one quiet sentence of what is safe, Sync now (disabled offline / while syncing), Storage & sync settings. `useOnline(force?)` is the one `navigator.onLine` subscription; `connectionCopy({online,pending,syncing,lastSynced,failed})` is the one copy source — "You're offline — 3 edits waiting to save · They save when the connection returns. Keep this tab open: reloading or closing it discards them. Last saved 12 minutes ago." In the app (`app/saveState.ts`) the numbers are TanStack Query's own mutation cache: waiting = paused offline (in this tab's memory — there is no durable replay yet, and the copy never claims "saved on this device"), "Syncing" only for a save in flight longer than 700ms, and "2 not saved" (`circle-alert`, Dismiss in the menu) for edits the server refused, each already rolled back with its reason in a message. While edits wait or travel, leaving the page asks first (`beforeunload`). The app route checks the session once per page load, so in-app navigation works offline, and Settings is fetched at idle so Storage & sync opens offline too. Pages without a top bar render `SyncNotice` with that copy (`tone`/`icon`/`message`/`detail`). Settings › Storage & sync › Offline editing shows the same numbers as rows; a failed push once back online is the existing danger `SyncNotice`. Connectivity is never a Toast. Card: Connection status (Components).
- **Kit:** "Trade show 2027" (Sales) opens to the empty-project state; "Dealers & stock" fetches on first open (skeleton) and shows a failed sync (first Retry fails again, second succeeds); any filter combination with no hits shows the no-match state; deleting or filing every Inbox item shows the empty inbox. `?offline` forces the connection down (3 edits queued, every edit adds one), `?offline=8` reconnects after 8 seconds so the pill plays Offline → Syncing → Synced.

## NOTIFICATIONS (they are Inbox items)

There is no bell, no notification panel and no notification list in Settings. Every message that is not transient becomes an **item in the account-level Inbox**, so nothing is lost: it is read, filed onto a project, checked off or deleted like any other item. The routing rule is `NOTIFICATION_SURFACES` in `components/core/Notifications.jsx`:

- **Toast** — you just did it and can undo it (moved, deleted, filed, exported), or a request you just made was refused. Gone in about 5 seconds.
- **SyncNotice** — a condition that holds right now (sync failed, offline, remote changes waiting). Stays while the condition does.
- **Inbox item** — everything else: a mention, an assignment, a comment or move on an item you watch, an invite, a sync conflict, a reminder, news from Todoi. Stays until you act on it.

An Inbox notification is a normal item built with `notificationItem({kind, from, about, text, detail, created})`, rendered by `ListRow` with three extra props: `from` (a 20px round `Avatar` of the member, or the square app tile with the kind glyph when Todoi itself sends it — `NotificationMark`), `about` (the key of the item it refers to, in mono at the right edge; clicking it opens *that* item — the notification has no key of its own), and `unread` (the existing Inbox unread treatment). The overlay shows the excerpt or next step as the description and lists the referenced item under **Related to**. Arrival is quiet: no toast, no sound — only the `UnreadBadge` dot on the sidebar Inbox row and the unread rows. The Inbox header carries **Mark all read** while anything is unread. Copy: actor first, past tense, then the key and title after a colon ("Sam Verhoeven mentioned you on MP-112: Pricing page"); app-sent titles start with the subject ("Sync conflict on MP-112 — changed in Todoi and on GitHub"). Settings › Notifications holds preferences only and points at the Inbox.

Inbox items are ordinary items with an Inbox scope (`app/inbox.ts` `useInbox`, the same `useProjectActions` and `ItemOverlayScreen` as a project with `projectId` null): a row opens the overlay (`/inbox?item=`, which also marks it read), where **Move to project…** takes the list select's place and labels / assignees (project features) are left out; the move, its toast and Undo are the cross-project move's. Dragging a row onto a sidebar project files it into that project's first list. ⌫ deletes with Undo; Create › Create an item opens the Inbox with the quick-add field focused (`?capture`).

## EXPORT & PRINT

An item or a view leaves Todoi in three formats — **PDF**, **Markdown**, **CSV** — from one component, `ExportMenu` (`components/core/ExportMenu.jsx`; `EXPORT_FORMATS`, `exportSummary`, `ExportButton`). Rows show the extension as a mono trail; one note says what goes out; an optional Print row.

- **View:** the Share dropdown ends with "Export this view" (`SubNavbar` `onExport`, `exportCount`, `exportFiltered`). The export takes what is shown — active filters and sort apply; the note reads "This board view · 12 items · filters applied".
- **Item:** the overlay's corner ⋯ gains "Export…" (a drill view; `ItemOverlay` `onExport`, `onPrint`, `printShortcut`) — the item with its subitems, description, attachment list and comments, plus Print.
- **Markdown round-trips:** it is the Embridge format Settings › Import reads. CSV is one row per item (Title, List, Status, Priority, Due, Labels, Assignee, Key). PDF and Print use the browser print pipeline with `tokens/print.css`: chrome (`.td-topnav`, `.td-sidebar`, `.td-subnav`), floating layers (toast, bulk bar, hint, popovers) and hover-only controls disappear; the overlay prints as a plain page; consumers add their own selectors to `[data-print="hide"]`.
- **Outcome is a toast** ("Exported “Website” board view as CSV — 12 items"), never a progress dialog. Card: Export & print (Components).

## RESPONSIVE

Todoi is **desktop-first** with three named device classes — **Desktop** (≥ 1024px, pointer), **Tablet** (768–1023px, touch + pointer), **Phone** (< 768px, touch) — plus a **touch flag** (`(hover: none) and (pointer: coarse)`). All of it is declared once, in `components/core/Viewport.jsx`: `useViewport()` returns `{device, touch}` and mirrors it to `<html data-device data-touch>`; `Chrome.jsx`'s `useDesktop()` (kit) delegates to it. **No component stylesheet contains a `@media` rule** — components branch on `html[data-touch="true"] …` / `html[data-device="phone"] …` or call `useViewport()`. Specimen pages force a class with `<html data-force-device="phone" data-force-touch="true">`.

**What the 1024px breakpoint does:** it moves the project nav, and nothing else.

- **≥1024px (desktop):** the `SubNavbar` (view switcher + Filter/Sort/Style + Share) is hoisted into the `TopNavbar` via its `children` slot, so the top bar carries title + search on the left and nav + avatar on the right in one row. `BoardHeader` is rendered with `hideNav` and contributes only its dropdown layer.
- **<1024px:** the top bar keeps only title, search, and avatar; `BoardHeader` renders the `SubNavbar` as its own row directly under it. Two rows instead of one.

**What the touch flag does (tablet and phone):**

- **Touch drag — `useTouchDrag` / `attachTouchDrag`** (`components/core/TouchDrag.jsx`): native HTML5 drag never fires on touch, so every screen that drags binds this pointer-event layer beside it — Board and List (items and subitems, kit screens), the overlay `Checklist` and `CalendarGrid` chips (inside the components). Long-press 350ms (≤ 8px slop) lifts: a clone with `--shadow-raised` follows the finger on `--z-drag`, the source dims (`.td-drag-src`), text selection and scrolling are held, a short haptic tick. `onMove` gets the point and the element under the finger, so the screen **reuses its `dragover` cue logic** — the same 2px blue slot line, `is-drop` cell tint and re-parent ring. Within 40px of a scrollable ancestor's edge the scroller auto-scrolls (≤ 14px/frame) and a 3px action-blue bar marks that edge. Release drops through the shared handler (same toasts, same aria-live); Esc or pointercancel cancels; the click after a drop is swallowed. Interactive children (buttons, checkboxes, inputs, open menus) never lift. No tilt, no scale. Card: Touch drag and drop (Interaction).
- **Hover-revealed controls stay visible:** under `html[data-touch]` the card ⋯, checklist row ⋯ and header actions, and attachment Open / ⋯ render always; the checklist drag grip hides (long-press replaces it); tapping a card or row key copies it and shows the check for 1.2s. Swipe-to-reveal was rejected — it hides the same controls behind an untaught gesture.
- **Hit targets:** menu rows, checklist rows and attachment rows grow to 44px; `IconButton` keeps its 24–32px look and gains an invisible 44px hit area (`::after`). Checkboxes (20px) and the aside buttons outside the phone sheet are still small.
- `ShortcutHint` and kbd chips are pointer nudges — consumers should not mount `ShortcutHint` when `touch` is true.

**What the phone class does:**

- **Item overlay → full-screen sheet.** `Modal` (and so `ItemOverlay`) reads `useViewport()`; on phones (or with `sheet`) the panel fills the viewport, slides up 200ms, and stacks: a sticky title row with key · link · ⋯ · close, the aside as a section directly under it (`.td-aside-stack` becomes a two-column grid of 44px property rows), then description, subitems, attachments and the activity thread. `sheet={false}` opts out.
- **Popover → bottom sheet.** One variant in `Popover` (`sheet="auto"` default; `true`/`false` to force) covers every `Menu`, `MenuButton`, `Select` and picker: portal to body, own backdrop on `--z-sheet` (150), 36×4 grab handle (swipe down 80px dismisses), radius 12 top corners, 44px rows at 15px, safe-area padding, focus return to the trigger. Anchored placement, flip and `width` are ignored in sheet mode.

**Fluid behaviour that exists independently of the breakpoint:**

- **Board:** `overflow-x: auto` on the canvas; lists stay fixed at `--size-list-width` (275px) and never shrink, so narrow viewports scroll horizontally rather than reflowing.
- **List view:** single column, `max-width: 900px`, centred; fills narrower viewports edge to edge inside its 20px padding.
- **Overlay (desktop/tablet):** `width: var(--size-overlay-width, 880px)` with `max-width: 100%`, sitting in a backdrop with 16px side padding; the aside is capped at `max-width: 45%` of the panel, so it narrows before the main column does.
- **Sidebar:** fixed width, capped at 264px; collapses to width 0. Collapse is driven by the `TopNavbar` toggle (a user action), not by viewport width.
- **Command palette:** `width: 560px; max-width: 100%`.

**Still open** (tracked in the **Desktop · Tablet · Phone** card, `guidelines/responsive.html`): the project nav overflows under ~560px (needs a compact switcher); the board should become one list per screen with scroll-snap on phones; the month grid is unreadable below ~480px (Day/Week should be the default); the sidebar overlay has no backdrop or swipe-to-close; Toast and BulkBar collide under ~600px. A consumer adding those extends `Viewport` and the touch cards — and updates the table first rather than scattering `@media` rules through components.

## Intentional additions

- `Icon` (components/core): thin wrapper over the Lucide CDN registry so React components share one glyph API. Needed because no icon assets could be copied from the source.
- `Toast`, `CommandPalette`, `ShortcutsDialog`, `KeyNav`, `FilterChip`, item keys, and the keyboard model (see INTERACTION & KEYBOARD): original power-user additions for coder/technician audiences, not present in the source screenshots — styled strictly from existing tokens.

## Secondary pages (/settings, /account)

Both pages share one shell (`ui_kits/todoi/SettingsScreen.jsx`) built to absorb many options without a redesign. Vocabulary: **Page › Section › Group › Row**. The page nav (200px, on the chrome, sidebar-row styling with the white selected pill) lists both pages as headers with their sections beneath; the content column (max 640px) stacks one white card per group; a card is a stack of 44px rows separated by `--border-divider`, each row = label + optional 12px hint on the left and exactly one control on the right (select, switch, text field, button, swatch group, read-only mono value, link, or a ⋯ menu). ## PROJECT LIFECYCLE (create, settle, leave)

A project is created in a dialog, settled from inside itself, and every change to it is written to one log. All three surfaces live in `components/project/` and use the Account row idiom (label + hint left, exactly one control right) so nothing new has to be learned.

- **Create — `ProjectDialog`** (on the shared `Dialog`, `components/core/Dialog`): every "+" that used to add a bare "New Project" row (sidebar group +, Projects +, Account › New project) opens it instead. One screen: the icon/color tile (`ProjectIconPicker`) in front of a 36px name field, then Project group (Select, preselected to the last-active group), **Start from** — a radio list of templates from the `PROJECT_TEMPLATES` registry (Blank · To-do, Doing, Done · Intake · Weekly plan; each template names its lists and the Status role each list links to) plus "Copy an existing project" (lists and settings, never the items), and Visibility (Private · Shared · Public — `PROJECT_VISIBILITY`, the same three the Members dropdown offers). Enter creates, Esc cancels, Create stays disabled until there is a name. `kind="group"` is the same dialog for a project group: name + an Item ID prefix pre-filled by `suggestAbbr` ("Sales" → SAL), 2–5 letters or digits, with the example key under it. The new project opens at once; the toast names the group and the seeded lists.
- **Settle — `ProjectPanel`**: the project's settings from the project itself — sidebar project ⋯ › **Project settings** (first row), the Projects page ⋯, the Members dropdown's "Invite members…" / "Member settings & roles" — never only from Account. A 640px `Dialog` headed by the icon/color tile (tap to change) and the name with its group as a crumb, plus a Copy-link icon beside Close (the item overlay's corner-link idiom; swaps to a check for 900ms), then **one scrolling body, no tabs**, titled sections ordered by how often they're touched: Name; Access (Visibility); Members (the roster with a role Select — Admin · Editor · Viewer; Owner is text — and a remove × for admins, plus an invite-by-email field + role); Defaults (Default view — applied when a project opens for someone who hasn't picked a view this session; Link lists with statuses — the same per-project toggle the Projects page shows; Item ID prefix, read-only because it belongs to the group); Appearance (Icon and color, Description — a textarea that shows Save / Cancel only once edited; both without hint text — the control explains itself); Activity (the log below); Leave and archive (Leave project — an owner must transfer first; Archive — admins; Delete — owner, red). **Destructive rows confirm inline on the row** ("Archive “Name”?" · Archive · Cancel), never in a second dialog. `tab="members"` / `"activity"` scrolls the body to that section on open. Non-admins see everything read-only. Account › Projects keeps storage, share links and invites — the panel covers what a member needs day to day.
- **Log — `ActivityLog`**: activity was per item only; the project log is that rail across the whole project. ## ARCHIVE & TRASH (restore later)

Archive and Delete are two different distances. **Archive** puts a project or item out of the way for good — hidden from the sidebar, views, search and counts — but keeps it. **Delete** moves it to the **Trash**, where it stays 90 days (`ARCHIVE_RETENTION_DAYS`) and is then removed for good. Both still raise the undo toast at the moment they happen; the view below is for later. Only "Delete forever" (from the Trash) is permanent, and it confirms inline on the row.

- **`ArchiveView`** (`components/project/ArchiveView.jsx`): one block — an Archive · Trash `Segmented` with counts, a search field, a project filter `Select` (account scope only), a one-line caption ("Archived projects and items are out of the way but not gone. Restore puts them back where they were." / "…kept for 90 days, then removed for good."), then a white card of 44px rows: a 28px lead (project tile, or the item's list/status glyph — done items keep the green check), title, one meta line ("Archived by **Flo Zuallaert** · 3 days ago · Helicopters Europe website › Ongoing" / "Deleted by **Sam Verhoeven** · 12 days ago · gone in 78 days" — red once a week is left), the mono item key, a **Restore** button, and a hover ⋯ with Open · Delete (archive → trash) or Delete forever (trash: the row's meta asks "Delete “…” forever?" · Cancel · Delete forever). Empty trash confirms the same way in the bar. Rows group into Projects / Items only when both kinds are present; `EmptyState surface="card"` covers Nothing archived · Trash is empty · No matches. Restore is instant and puts things back exactly where they were (the list, the position, the project's members); the consumer raises the toast — "Restored “…” to Ongoing" with Undo. Restoring a project restores its items; restoring an item whose project is archived restores the project too (the toast says so).
- **Entry points — never a sidebar destination:** **Account › Data › Archive and trash** opens the account-wide view (every project the person can admin, with the project filter); **Project settings › Leave and archive › Archived items · View** (`ProjectPanel` `archivedCount`, `onAction("open-archive")`) opens it in project scope (`project` set — no filter, meta drops the project name); a project ⋯ menu's Archive / Delete keep their toasts. Subitems archive and delete with their item and are not listed on their own.
- **Kit:** not wired yet — the kit's Archive / Delete still end at the toast. Card: Archive and trash (Components).

- **`ResetPasswordPage`**: both ends of the reset flow, one card per `stage`. **request** — "Reset your password", Email, Send reset link, Back to log in (from "Forgot?" and from Account › Sign-in methods › Send reset link); **sent** — the same "Check your inbox" block as the magic link ("works once and expires in 1 hour"); **new** — what the emailed link opens: "Set a new password · for sam@…", one `PasswordField`, a "Log out other devices" checkbox (on by default), Save password and log in — no confirm field; **done** — "Password updated · You're logged in on this device and logged out everywhere else", Continue to Todoi; **expired** — a used or hour-old link: clock glyph, "This reset link has expired", Send a new link. Card: Sign-up and password reset (Components).
- **`InvitePage`** (`todoi.app/i/CODE`; the kit opens it with `?i=CODE` and from Account › Projects › invite ⋯ › Preview landing page): the project first — tile, name, "Group · n items · n members" — then "Flo Zuallaert invited you to join · as Editor · invite valid until Sep 30" and the description as a quiet quote. Exactly one next step per state: signed in → a "Joining as <avatar> name · email" block with "Not you?" and **Accept invite** / Decline; signed out → **Log in to accept** / Create an account with "The invite was sent to …"; expired → clock, "This invite has expired", ask the inviter; revoked → "This invite was withdrawn"; already a member / accepted → **Open project**.
- **Read-only guests — `GuestBar`**: a Public project opened without an account, or a Viewer inside one, gets the normal app frame with one extra 40px chrome row directly under the top bar: globe/eye glyph, "Public project · read only" / "View only", a dim hint, and Ask for access (→ "Access requested") · Create an account · **Log in** at the right. It never dismisses. The same stylesheet carries the **read-only contract**: `data-readonly="true"` on the content wrapper hides every add/edit affordance the views draw (Add an item, Add another list, list ⋯ menus, quick-add, the calendar's day plus) and makes checkboxes and list names inert, and no card, row or calendar chip lifts on drag (native or touch), while cards and rows stay clickable — the item overlay opens with only its read-only rows (a missing callback hides a row). A private project seen signed-out is not a guest view; it is the sign-in page with that context.
- **Kit:** log out on a Public project (Members dropdown › Public) to get the guest view; on a private one you land on the sign-in page (any provider button or a password logs you back in). `?i=demo` opens the invite landing signed out; Log in to accept returns you to it signed in, Accept joins and writes the member entry to the log.

## Views

Content renders in three switchable views — **List is the default view** (on first load and for a fresh project); navigating between projects or in and out of secondary pages (Groups, Projects, Inbox, Settings) never changes the current view. The `SubNavbar` switcher (`views`/`activeView`/`onViewChange`) ships all three by default:
1. **Board** (kanban glyph) — built: `components/board/`; `BoardView` is the assembled top-level container (ListColumns on the canvas + "Add another list").
2. **List** (list glyph) — built: `components/list/`; `ListView` is the assembled top-level container (ListSections stacked on the canvas + "Add another list"). Minimal by design: flat 32px rows, circle checkbox completes an item, square checkboxes on subitems.
3. **Calendar** (calendar glyph, labeled "Cal.") — built: `components/calendar/`; `CalendarView` is the assembled top-level container. Month grid by default; the header dropdown switches Day / Week / Month / Year. Items land by due date (done items keep the green check); an item with a start date before its due date renders as a multi-day span bar in the first label's color. Overflowing cells collapse to a measured "+N more" that jumps to the day view; drag a chip to another day to reschedule (undo toast in the kit); click an empty day to add an item; arrows move day focus, ←/→ outside the grid (and PageUp/PageDown anywhere) change period. Undated items stay off the calendar by design — no tray and no header control at launch; the List view is where undated items are found and scheduled until a dedicated calendar flow is designed.

## Lists & Status linking

List and Status are separate concepts, linked only by explicit configuration — never by matching title text.

- **Statuses:** the canonical registry (`STATUSES` in `components/core/StatusChip.jsx`) ships five statuses with **stable ids** `NEW / BACKLOG / TODO / DOING / DONE`. Store and link by id; names are display copy and safe to rename. **`None` is an item's default Status** — the overlay's Status dropdown lists it first and `onSetStatus` reports it as `null`. With "Link Lists with Statuses" on, items in lists that carry a role usually pick one up on create/move, but a Status is never guaranteed. **Status glyphs** (all in the dial family): New `circle-dashed`, Backlog `archive`, To-do `circle-todo` (custom: ring + hand at 12, "dial at zero" — never plain `circle`, which reads as an empty checkbox next to the row checkbox), Doing `circle-dot` (blue), Done `circle-check` (green). `listIconFor("To-do")` returns the same `circle-todo` and `listIconFor("New")` returns `circle-dashed`, so New and To-do lists share their status's icon.
- **Status role:** a list may carry an optional role (a stable status id; `None` is a normal state). Set it in the list-actions menu ("Status role" row — a "Suggested" hint prefills from `suggestedRoleForTitle`, but the stored link is always the explicit id). "Manage list–status links…" opens the project-level overview (the Projects page). Renaming a list or a status never breaks the link.
- **Project automation setting:** the "Link Lists with Statuses" toggle on the Projects overview (per project, default ON) decides whether an item created in or moved to a list with a role takes that role's Status. Linked moves — drag, Ctrl/Cmd+arrow, "Move to list", bulk moves — update list and Status together, atomically; the toast reads "… — Status set to Doing" and undo restores both. Moves to unlinked lists, reorders within a list, drags while grouped by Status, and direct Status edits never cross over.
- **Changing a role never silently rewrites items:** `RoleReviewDialog` offers "Apply to existing items" (one explicit bulk update) or "Future moves only". Removing a role changes no item In the app the review is a `ConfirmDialog` ("Apply Doing to the 2 items already in “Backlog”?") shown before anything is saved, only when the list has live items; either answer is one request (`applyToExisting` for the first), which rewrites exactly the live top-level items it counted — archived ones keep their Status. Esc and the backdrop mean "Future moves only". Removing a role, or a role on an empty list, saves at once.
- **Hiding a list is project-wide** (it is shared project data): the toast reads "Hid “Backlog” for everyone in this project" with Undo. After "Add another list", both views show a quiet "2 hidden lists" button (`HiddenListsMenu`) whose menu shows each one again (with its item count) or all of them. When every list is hidden the view says so ("All 3 lists are hidden" · Show all lists · Add a list) instead of the empty-project state.
- **Status display is a per-user preference**, not shared config: "Show Status on items" in Settings › Appearance (`When informative` default / `Always` / `Never`; `useAppearance().statusDisplay`). "When informative" shows the `StatusChip` only where it adds information — an unlinked list, a Status differing from the list's role, or a flat context; it stays hidden where the list role or a heading already says it. `Never` hides it on compact rows/cards only — the item overlay always offers Status. Grouping never activates, hides, or changes Status behavior.
- **Checkbox semantics:** checking sets Status to Done and remembers the prior Status; unchecking restores it.
- **Intentionally out of scope:** Status chips on calendar chips (deliberately not designed — the chips are too compact), a mirrored Status→List mode (would require one destination list per role), and Inbox role automation (the Inbox is one app-managed list).
